# M2a Summary: Content-Management API

**Branch:** `feat/m2a-content-api`, merged via PR. **Tests:** 215 passing with `-W error`.
M2a was built in two plans (part 1: publishing and hardening; part 2: editorial and feeds). Each plan went task by task, with a Sonnet implementer and a Sonnet reviewer per task, then an Opus review of the whole branch and one fix wave.

## What was done
- **Per-language publishing.**
  - Each translation has its own status, `published_at` and `updated_at`.
  - A translation added to a live post stays private until an editor publishes it.
  - The public site, hreflang and alternates only include published translations.
  - Autosaving a draft translation, or saving a live post without changing anything, leaves the public site and the caches alone.
- **Editorial workflow.**
  - Submit, send back to the reporter, publish (If-Match), publish a single translation, unpublish to archived, and change category with automatic 301 redirects.
  - Revisions are kept for every real change to a published translation. Any revision can be restored as a normal versioned save.
- **Posts list** for the admin: filters, pagination and author names. Reporters only see their own posts.
- **User admin.** Admins create users, change roles, deactivate accounts and reset passwords. Users edit their own profile and password. Emails are always stored in lower case. An admin cannot demote or deactivate themselves.
- **Categories and tags.**
  - Categories form a tree up to 3 levels deep, with cycle protection and a lock so two editors can't create a cycle at the same time.
  - A category that still has posts can't be deleted.
  - There is a public category tree endpoint. Tags can be attached to posts.
- **Search.** Full-text search on titles and bodies (works for Nepali text) plus typo-tolerant title matching. It only returns published content.
- **Public feeds for the website.** Home (breaking news plus the latest stories per category), category pages that include sub-categories, search, the category tree, single articles, and redirect lookup.
  - All feeds are cached in Redis.
  - Invalidation is precise: a site-wide generation counter for feeds, per-path keys for articles.
  - A cache outage, or unreadable old cache data, falls back to the database.
- **Slug changes and redirects.** Editors can rename a published article's address. The old address gets a 301, chains collapse, and no redirect can point to itself.
- **Hardening.**
  - JWTs must carry exp, sub and iat.
  - Failed logins take the same time whether or not the user exists.
  - Publishing requires If-Match.
  - Slug collisions are retried.
  - Database-conflict races return 409 instead of 500.
  - Server defaults are in place, and the migration drift check also compares them.

## Key decisions
- Editors may publish a draft that was never submitted.
- Category and tag slugs can't be changed. Restoring a revision doesn't change the slug.
- A send-back note travels in the outbox event.
- Search uses Postgres `simple` full-text search plus trigram word-similarity.

## Carried into M2b
- **Security:** rate limits for search and login; revoke tokens on a password change.
- **Content refresh:** refresh stored SEO when a category or author is renamed.
- **Edge cases:**
  - the race where two admins demote each other at the same time
  - send-back should require If-Match
  - normalise paths before redirect lookups
  - freeze a copy of `plain_text` inside the search migration
  - check slug format before caching a 404
  - paginate revisions
  - add a test for changing slug and category in one save
- **M2b scope:** the outbox worker (ISR revalidation and Cloudflare purge), scheduled publishing (it must also publish translations), media/R2, .docx import, sitemaps/RSS, view stats, and refresh tokens with CSRF.
